# Реализация алгоритмов A1–A7 симулятора вождения

Процедурная реализация алгоритмов, разработанных в `UP-004` (схемы, таблицы шагов, каталог правил), для учебной практики «Разработка симуляторов вождения». Клиентские алгоритмы написаны на C# (библиотека для Unity), серверные — на Java. VR-сцены и Unity-проекта в этой версии нет: алгоритмы запускаются на подготовленных и записанных данных.

Объектно-ориентированная реализация сервера на Java со Spring Boot — следующий этап практики; процедуры из пакета `sim` станут её основой.

## Состав

```
data/                       справочные данные сервера: обучающиеся, три упражнения (сценарий и правила версии 1)
docs/message-format.md      формат JSON-сообщений клиент ↔ сервер
samples/trajectories/       записанные кадры движения (вход клиента): 15 случаев
samples/journals/           журналы событий (вход сервера): 31 случай; создаются серверными проверками
server-java/src/sim/        сервер: Prepare (A1), Receive (A4), Completeness (A5), Evaluate (A6, A6.1), Compare (A7),
                            Storage, Json, Geometry, HttpApi
server-java/src/checks/     ServerChecks — проверки серверных алгоритмов
unity-client/               проект Unity 6 (6000.6.7f1) с клиентскими алгоритмами в Assets/Scripts/Simulator:
                            Restore (A1), Registrar (A2), Delivery (A3), MessageJson, Models; файлы .meta сохранены
client-csharp/Simulator.Client/          сборка тех же файлов .cs вне редактора (netstandard2.1) для проверок
client-csharp/Simulator.Client.Checks/   проверки A1 (клиент), A2, A3
client-csharp/Simulator.Client.Demo/     генерация траекторий и сквозная демонстрация с сервером по HTTP
run_all.ps1                 сборка, все проверки и демонстрация одной командой
```

Клиентский код хранится в проекте Unity и не зависит от UnityEngine и сторонних пакетов; язык ограничен C# 9. Проект `Simulator.Client` в `client-csharp` собирает те же файлы командой `dotnet`, поэтому проверки запускаются без редактора. Компиляция в самом Unity (6000.6.7f1, режим batchmode) выполняется командой из раздела «Запуск». Сервер не использует внешних библиотек: JSON разбирает собственный класс `Json`, HTTP — встроенный `com.sun.net.httpserver`.

## Требования

JDK 17 и новее (проверено на JDK 25), .NET SDK 8 и новее (проверено на SDK 8, 9, 10), Windows PowerShell 5.1 для `run_all.ps1`; Unity 6000.6.7f1 нужен только для компиляции в редакторе. Подключение к сети и установка пакетов не нужны.

## Запуск

Все проверки и демонстрация (из каталога `code`):

```bash
powershell -ExecutionPolicy Bypass -File .\run_all.ps1
```

Скрипт выполняет семь шагов и сохраняет вывод каждого в `out/logs`: сборку Java, серверные проверки, сборку C#, клиентские проверки, запись траекторий, сквозную демонстрацию (нормальный канал и канал с отказами, сравнение попыток) и проверку истории после перезапуска сервера. При любой неудаче скрипт останавливается с ненулевым кодом.

Отдельные части:

```bash
javac -encoding UTF-8 -d out/server server-java/src/sim/*.java server-java/src/checks/*.java
java -Dstdout.encoding=UTF-8 -cp out/server checks.ServerChecks
dotnet run --project client-csharp/Simulator.Client.Checks -- data
```

Сервер отдельно: `java -cp out/server sim.HttpApi --port 8080 --data data --store out/store`.

Компиляция клиентских скриптов в Unity без открытия редактора (путь к редактору зависит от установки):

```bash
"C:\Program Files\Unity\Hub\Editor\6000.6.7f1\Editor\Unity.exe" -batchmode -nographics -quit -projectPath unity-client -logFile out/unity-compile.log
```

В журнале не должно быть строк `error CS`; при успехе есть строка `Csc … Assembly-CSharp.dll`.

## Как проверить работу

1. Серверные проверки (`checks.ServerChecks`) выводят строки `[OK]`/`[FAIL]` и итог «выполнено N, ошибок 0». Ожидаемые результаты заданы в самих случаях: для каждого правила каталога — правильное выполнение и ошибка; перечень ошибок, статус и признак окончательности сверяются с определением случая.
2. Клиентские проверки (`Simulator.Client.Checks`) — то же для A1 (клиент), A2 и A3.
3. Сквозная демонстрация воспроизводит 15 записанных траекторий через A1 → A2 → A3 → HTTP → A4 → A5 → A6 и сравнивает результат сервера с ожидаемым, заданным в файле траектории. Во втором проходе канал обрывается на четыре отправки подряд, один раз отвечает 503 и один раз теряет подтверждение: результат должен остаться тем же, а повторно доставленная группа не должна создавать новых записей.
4. Воспроизводимость: повторный запуск `run_all.ps1` даёт те же результаты (идентификаторы попыток `a-0001`, `a-0002` … назначаются по порядку).

### Уточнения, которых нет на схемах

Реализация потребовала решений, которых нет на схемах; они не меняют условий и переходов:

- A1: идентификатор попытки — следующий номер `a-NNNN` в хранилище (воспроизводимость проверок); момент создания передаётся в процедуру параметром.
- A2: первый кадр только запоминает сторону стоп-линии и признак «внутри участка»; событий не создаёт. Пересечение стоп-линии считается только в пределах её длины и только по ходу движения (знак расстояния меняется с отрицательного на неотрицательный). Пустая группа не отправляется.
- A3: процедура возвращает управление вместо бесконечного ожидания (блок 3) и может вернуть `Suspended` после заданного числа неудач подряд — так её вызывают на каждом кадре, не блокируя отображение. Пауза — делегат `wait`, поэтому в проверках используется виртуальное время.
- A4: формат сообщения о завершении схемой не проверяется (блок 4 ведёт сразу к блоку 6); некорректный JSON отклоняет HTTP-слой кодом 400.
- A6: результат записывается без названия упражнения и длительности (они берутся из `Exercise` и `Attempt`); эти поля добавляются в ответ при показе (блок 14).
- A7: неизвестная попытка даёт 404; отсутствие результата у одной из попыток рассматривается как предварительный результат.

## Ограничения этой версии

- Проект Unity содержит только клиентские алгоритмы: сцены, физики автомобиля, VR и устройств управления нет; траектории — детерминированная кусочно-линейная кинематика (`Trajectories.cs`), а не результат движения WheelCollider.
- Сервер — процедурный прототип на встроенном HTTP-сервере JDK; Spring Boot, классы правил оценки и объектная структура — следующий этап.
- Очередь клиента хранится в памяти процесса; сохранение очереди на диск не реализовано.
- Плавность изображения, обзор из кабины и совместимость оборудования не проверялись: этих компонентов в версии нет.
